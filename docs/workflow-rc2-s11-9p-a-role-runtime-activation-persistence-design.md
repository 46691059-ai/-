# Workflow V1 RC2-S11.9P-A ROLE Runtime Activation Persistence Design

## Current State Assessment

The audited baseline is commit `82945b58e751a3922db87ac721c5e946b49a8f84`. The immutable release tag `workflow-v1.0.0-rc2.1` resolves through tag object `269595532f17cc3db09880404ca11629d108fc6d` to release commit `c5946d272e8eb88115671d66b46e8c8ec67b1477`.

Read-only inspection of `127.0.0.1:3306/enterprise_platform` found exactly one matching six-dimensional Canary scope. Its latest state is `ENABLED`, revision 3, with exactly one `ENABLED` event. The three existing ROLE Runtime approval-persistence tables contain zero rows. ROLE Runtime is therefore `DISABLED`, its activation event count is zero, and the frozen Kill Switch remains `STOP_NEW_AND_CLAIM`. Workflow task and claim counts are zero.

Existing capabilities are deliberately limited:

- `role_runtime_activation_request` stores an append-only persisted request and its hashes.
- `role_runtime_activation_approval` stores append-only RACI decisions.
- `role_runtime_activation_evidence` stores append-only hash evidence associated with an approval.
- Their domain repositories, MyBatis mappers, entities, and `RoleRuntimeActivationPersistenceService.persistApproved` are reusable as the approval/evidence source.
- There is no runtime-activation event entity, repository, mapper, state derivation repository, or application write path.

The existing approval lifecycle and the new runtime lifecycle must not be mixed. Canary governance records must not be reused or mutated.

## Blocking Gap

`RoleRuntimeActivationPersistenceService` explicitly exposes no enable operation. `PersistentActivationStatus.PERSISTED` means only that the approved request/decision/evidence set was durably frozen. No database fact proves that ROLE Runtime was activated, and no transaction provides idempotency, replay protection, stale-authorization rejection, or database-backed concurrency control. This confirms the S11.9A fail-closed reason.

## Domain Lifecycle Separation

Keep `PersistentActivationStatus` unchanged as the approval/evidence persistence lifecycle:

`DRAFT -> SUBMITTED -> APPROVAL_PENDING -> APPROVED -> PERSISTED`, with the existing terminal rejection/revocation/block states.

Introduce an independent runtime lifecycle:

`DISABLED -> ACTIVATED`

and a single initial event type:

`ROLE_RUNTIME_ACTIVATED`

The term `ENABLED` is not used for the ROLE runtime event or resulting state, avoiding collision with Canary enablement. A `PERSISTED` approval is a prerequisite, never proof of `ACTIVATED` runtime state.

## Persistence Model

Choose option A: an append-only activation event with state derived from the latest valid event. No current-state projection is required for this exact-scope, one-way initial lifecycle. The event is the authoritative audit source; absence of an event means `DISABLED`, and one valid `ROLE_RUNTIME_ACTIVATED` event means `ACTIVATED`.

This matches the repository's append-only governance architecture and eliminates the atomicity split that a separately updated projection would introduce. If later suspend/reactivate transitions make read cost material, a projection may be introduced by a separate migration and gate, but it must be transactionally updated and rebuildable exclusively from events.

The existing request, approval, and evidence tables remain the authorization source. The new event holds immutable structured scope and frozen bindings, and references the persisted approval request through `authorization_id`. No update is made to the approval evidence when activation occurs.

## Event Schema

Migration V2.6.25 should create `workflow_role_runtime_activation_event` with:

| Column | Proposed definition | Purpose |
| --- | --- | --- |
| `id` | `BIGINT NOT NULL` | Primary key generated by the existing identity generator |
| `event_id` | `VARCHAR(100) ASCII BIN NOT NULL` | Globally unique idempotency/audit identity |
| six scope columns | five `BIGINT NOT NULL` plus `role_code VARCHAR(100) ASCII BIN NOT NULL` | Exact scope, with no wildcard semantics |
| `event_type` | `VARCHAR(40) ASCII BIN NOT NULL` | Constrained to `ROLE_RUNTIME_ACTIVATED` |
| `sequence`, `revision` | `BIGINT NOT NULL` | Positive, immutable per-scope ordering; initial values are 1 and 1 |
| `previous_state` | `VARCHAR(20) ASCII BIN NOT NULL` | Constrained to `DISABLED` for the initial event |
| `resulting_state` | `VARCHAR(20) ASCII BIN NOT NULL` | Constrained to `ACTIVATED` |
| `authorization_id` | `VARCHAR(100) ASCII BIN NOT NULL` | Independent `ACTIVATE_ROLE_RUNTIME` approval identity |
| `authorization_type` | `VARCHAR(40) ASCII BIN NOT NULL` | Constrained to `ACTIVATE_ROLE_RUNTIME` |
| four commit columns | `CHAR(40) ASCII BIN NOT NULL` | Authorization, observation evidence, runtime enablement evidence, and release commits |
| `runtime_release_tag` | `VARCHAR(100) ASCII BIN NOT NULL` | Frozen release tag |
| six evidence hashes | `CHAR(64) ASCII BIN NOT NULL` | Directory result, version binding, manifest, content, structural fingerprint, and approval evidence hashes |
| `actor_type` | `VARCHAR(32) ASCII BIN NOT NULL` | Constrained human/service actor category |
| `actor_id` | `VARCHAR(100) NOT NULL` | Audited executor identity |
| `occurred_at`, `created_time`, `updated_time` | `DATETIME(3) NOT NULL` | Millisecond precision, UTC at the application boundary |
| standard audit columns | existing project conventions | `created_by`, `updated_by`, `deleted=0`, `delete_token=0`, `version=0`, optional remark |

Primary and database constraints:

- `PRIMARY KEY (id)`.
- `UNIQUE (event_id, delete_token)` for transport/idempotency identity.
- `UNIQUE (enterprise_id, organization_id, definition_id, definition_version_id, node_id, role_code, event_type, delete_token)` as the final concurrency barrier: only one activation fact per exact scope.
- `UNIQUE (enterprise_id, organization_id, definition_id, definition_version_id, node_id, role_code, sequence, delete_token)` and an equivalent revision unique key.
- Composite foreign key `(authorization_id, delete_token)` to the existing request owner key `(activation_id, delete_token)`.
- Checks for positive ids/sequence/revision, nonblank binary role identity, allowed event/state pair, lowercase SHA-1 commit shape, lowercase SHA-256 hash shape, and immutable soft-delete/version values.
- Index `(authorization_id, authorization_type)` for replay and audit lookup; the scope unique keys also serve latest-state queries.
- `BEFORE UPDATE` and `BEFORE DELETE` triggers reject mutation. An insert guard verifies the referenced request is `PERSISTED`, its approval evidence hash matches, and all three required approver decisions and evidence classes exist. Application validation remains mandatory; database constraints are the last defense.

Use InnoDB, `utf8mb4_0900_ai_ci` as table default, and explicit `ascii_bin` on machine identities, commits, tags, states, and hashes. All timestamps use `DATETIME(3)`, matching current migrations. Flyway must apply the DDL as one forward-only V2.6.25 migration after a fail-closed preflight that proves the table and triggers do not already exist. Rollback is operational restore from a pre-migration backup or a separately reviewed compensating migration; destructive down SQL is not embedded in Flyway.

## Authorization Binding

`ACTIVATE_ROLE_RUNTIME` is a new, explicit human authorization, distinct from Canary `APPROVE` and `ENABLE`. Its immutable `authorization_id` resolves to a `PERSISTED` request plus the required approval/evidence rows. The execution command also supplies `authorization_commit`; this and the canonical approval evidence hash are copied into the event.

Before insertion, the application reconstructs the canonical authorization payload and requires exact equality across authorization id/type/commit, exact scope, release identity, evidence commits, and hashes. A valid replay must use the same authorization identity and bindings. A different authorization against an already-active scope is rejected as stale/invalid rather than reported as a valid replay.

## Scope Binding

The activation API accepts a typed scope containing exactly:

- `enterpriseId=990001`
- `organizationId=990101`
- `definitionId=990401`
- `definitionVersionId=990402`
- `nodeId=990404`
- `roleCode=RC1_TEST_CANARY_APPROVER`

Every lookup and unique key uses equality on all six dimensions. Columns are non-null. There is no parent traversal, wildcard, omitted-dimension default, or cross-scope fallback.

## Evidence Binding

The activation event freezes:

- Canary observation evidence commit `82945b58e751a3922db87ac721c5e946b49a8f84`.
- Runtime enablement evidence commit `fd833003e6134b7c0e39a08d513fd0aa2af195eb`.
- Runtime release commit `c5946d272e8eb88115671d66b46e8c8ec67b1477` and tag `workflow-v1.0.0-rc2.1`.
- Directory result, version binding, manifest, content, structural fingerprint, and approval evidence hashes.

The application re-derives current evidence and compares it byte-for-byte with both the authorization and event command. Any mismatch makes authorization stale and fails closed before insert.

## Concurrency Model

The transactional application path first locks the exact latest Canary governance row and the referenced activation request (`SELECT ... FOR UPDATE`) in a documented, consistent order. It then queries the activation event by exact scope. The scope/event-type unique constraint is the final defense if two transactions race despite locking.

On a duplicate-key conflict, the service reloads the single event in a new/read-after-rollback transaction. It returns `ALREADY_ACTIVE` only when authorization id, authorization commit, all six scope values, release identity, evidence commits, and hashes exactly match. Otherwise it throws a stale/conflicting-authorization error. Java `synchronized` is neither required nor accepted as the concurrency guarantee.

## Idempotency Model

First valid command: insert one event and return `ACTIVATED`.

Same authorization and exact canonical payload replay: insert nothing and return `ALREADY_ACTIVE`.

Same scope with changed authorization or bindings: insert nothing and fail closed. Same authorization used for another scope: fail closed. The invariant is `ROLE_RUNTIME_EVENT_COUNT=1` for the authorized exact scope.

## Transaction Model

`RoleRuntimeActivationApplicationService.activate(command)` is a single Spring transaction:

1. Validate the independent authorization and its `PERSISTED` approval trail.
2. Validate immutable release tag/commit identities.
3. Validate observation and runtime-enablement evidence identities.
4. Lock and validate Canary latest state `ENABLED`, revision 3, and total enable-event count 1.
5. Validate the exact six-dimensional scope and all business evidence hashes.
6. Validate Kill Switch `STOP_NEW_AND_CLAIM` through its read-only governance provider.
7. Lock/check the runtime activation event; derive current state as `DISABLED` when absent.
8. Append `ROLE_RUNTIME_ACTIVATED` with sequence/revision 1 and derive `ACTIVATED`.
9. Commit.

Any error before or during insert rolls back the transaction. Because state is derived from the event, `ACTIVATED` without an event and an event with `DISABLED` state are structurally impossible.

## Kill Switch Isolation

The activation transaction has no Kill Switch writer dependency. It only verifies that the current value is `STOP_NEW_AND_CLAIM`. The event schema contains no Kill Switch mutation field. Postcondition validation requires the same value after commit.

## Traffic Isolation

Activation does not create tasks, populate candidate pools, execute claims, release traffic, provision infrastructure, bootstrap governance, or change Canary state. The application service must not depend on task creation, claim, routing, or traffic-release command ports. Those actions require later independent gates.

## Migration Design

The canonical migration directory contains V2.6.24 as its highest version; no V2.6.25 or higher canonical migration exists. V2.6.25 is therefore the next available version. It creates only the activation event table, constraints, indexes, foreign key, append-only triggers, and insert validation trigger described above. It performs no data backfill and no update of existing Canary or approval rows.

Implementation must add a migration contract test and run it against a disposable MySQL 8.4 database before applying it to any RC2 runtime. This design gate does not create or execute SQL.

## Test Strategy

- `RoleRuntimeActivationDomainTest`: independent `DISABLED -> ACTIVATED` lifecycle and prohibited state/event names.
- `RoleRuntimeActivationApplicationServiceTest`: all ordered preconditions and successful append behavior.
- `RoleRuntimeActivationIdempotencyTest`: identical replay returns `ALREADY_ACTIVE` and count remains one.
- `RoleRuntimeActivationConcurrencyTest`: two concurrent transactions produce exactly one event; loser resolves only a byte-identical replay.
- `RoleRuntimeActivationTransactionAtomicityTest`: failures before and during persistence leave zero events and derived `DISABLED` state.
- `RoleRuntimeActivationStaleAuthorizationTest`: every scope, commit, release, and evidence-hash drift fails closed.
- `RoleRuntimeActivationKillSwitchIsolationTest`: required value is checked and never mutated.
- `RoleRuntimeActivationExactScopeTest`: nulls, wildcard-like values, parent/cross-scope lookups, and one-dimension drift are rejected.
- `V2625RoleRuntimeActivationRealMysqlTest`: MySQL 8.4 DDL, foreign keys, checks, triggers, duplicate/replay race barrier, append-only enforcement, precision, charset, and collation.

Additional repository/mapping tests must prove exact binary lookups and deterministic duplicate-key classification. Governance regression must assert no dependency on task, claim, traffic, Canary mutation, or Kill Switch write ports.

## S11.9P-B Implementation Boundary

S11.9P-B may implement V2.6.25, the independent domain event/state types, repository/entity/mapper, the transactional application path, and the tests above. It may validate against a disposable database. It must not apply the migration to the protected RC2 runtime, create an activation event there, activate ROLE Runtime, release traffic, create tasks, execute claims, change the Kill Switch, move the release tag, or mix activation state into `PersistentActivationStatus`.

## S11.9A Re-entry Criteria

Re-enter S11.9A only after S11.9P-B proves all of the following:

- V2.6.25 and its real-MySQL contract pass on an authorized disposable database.
- The independent event repository and `activate` transaction exist.
- Exact scope, authorization/evidence/release bindings, stale checks, idempotency, replay, database-backed concurrency, and atomicity tests pass.
- Kill Switch and traffic isolation regressions pass.
- RC2 runtime remains `ROLE_RUNTIME=DISABLED` with zero activation events until a separate migration/application gate and explicit activation decision authorize changes.
