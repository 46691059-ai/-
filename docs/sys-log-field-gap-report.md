# sys_log字段缺失报告

## 检查结论

`sys_log`现有字段能够保存用户ID、操作描述、请求地址、请求方式、IP、执行结果、异常信息、耗时、TraceId及通用审计字段，但不能完整一对一承载Sprint 1-5要求。

| 审计要求 | 现有字段 | 结论 |
|---|---|---|
| 用户ID | user_id | 满足 |
| 用户名 | 无独立字段 | 缺失；正常用户通过sys_user关联，账号不存在的登录失败记录存入脱敏上下文 |
| 日志类型 | 无独立字段 | 缺失 |
| 模块名称 | 无独立字段 | 缺失 |
| 操作名称 | operation | 满足 |
| 请求地址 | request_url | 满足 |
| 请求方式 | request_method | 满足 |
| 请求参数 | 无独立字段 | 缺失 |
| 响应结果 | 无独立字段 | 缺失 |
| IP | ip | 满足 |
| 耗时 | duration_ms | 满足 |
| TraceId | trace_id | 满足 |
| 状态 | result | 满足 |
| 异常信息 | error_message | 满足 |

## 当前Sprint兼容方案

不修改数据库结构：

1. `operation`使用`日志类型|模块|操作名称`格式，最大100字符。
2. `remark`保存经过脱敏和长度限制的JSON上下文，包括用户名、请求参数及响应摘要，最大500字符。
3. 查询接口在Service层拆分标准化操作标识并解析上下文，向前端输出独立字段。
4. 密码、JWT、Authorization、身份证号等字段不保存原值；手机号按中间四位掩码处理。

## 后续建议

如需长期高容量审计、复杂统计或合规归档，应在独立数据库变更Sprint评审后增加`username_snapshot`、`log_type`、`module_name`、`request_params`、`response_summary`等物理字段，并为类型、模块、状态和时间建立组合索引。本Sprint不执行该变更。

现有索引可覆盖按用户/状态结合时间的查询和TraceId定位，但仅按时间范围查询、按`operation`拆分出的类型/模块查询，以及兼容上下文中的用户名模糊查询无法稳定命中索引；日志规模扩大后存在全表扫描风险。建议在上述数据库变更Sprint一并评估归档分区、独立`create_time`索引及类型/模块组合索引。
